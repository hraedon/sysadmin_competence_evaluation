# Domain 18: Minimum Viable Database Administration

*The database is state, everything else is replaceable*

## Scope and Framing

This is a compact domain. It is not a DBA certification, and it does not attempt to produce database administrators. It covers the functional floor for sysadmins who encounter databases in the wild — which is to say, all of them. The "minimum viable" framing follows the model established by Domain 12 (Minimum Viable Linux Administration): not expertise, but enough to operate without immediately handing off, enough to recognize the failure modes specific to the domain, and enough to know when the problem exceeds the floor and a specialist is needed.

The "minimum viable" bar is lower for databases than for Linux because the specialist boundary is closer. A sysadmin who never touches a Linux server will struggle in most modern environments. A sysadmin who never administers a database directly can still be effective — as long as they can recognize database-specific failure modes, back up databases correctly, and escalate at the right moment. The floor is not "can run a database." It is "can keep a database running long enough to get the right person involved, and will not destroy data in the attempt."

The contexts a sysadmin encounters databases: a business application with a database backend that is the sysadmin's responsibility to keep running, a database server that shares infrastructure with systems the sysadmin manages, a backup system that needs to protect database data correctly, and a monitoring stack that needs to alert on database-specific failure modes. In all of these contexts, the sysadmin is not the database specialist. They are the person who notices the problem, takes the right first diagnostic steps, and knows when to call someone who does this for a living.

*The assessment bar is not 'can administer a database.' It is: given a database in a context a sysadmin will actually encounter, can you keep it running, back it up correctly, recognize the failure modes that are specific to databases, and know when the problem is beyond this domain and requires a DBA?*

In most organizations the DBA is a business-hours resource. The sysadmin is the one paged at 3 AM when the monitoring fires. This means the sysadmin needs enough database knowledge to triage — to read the error message, form a hypothesis, take the diagnostic steps that do not require specialist knowledge, and make a defensible call about whether to attempt a fix or wait for the DBA. The sysadmin who can do this well reduces the blast radius of every database incident. The sysadmin who cannot do this either wakes the DBA for problems that do not require it (eroding the escalation relationship) or attempts fixes that make the problem worse (eroding the database).

The diagnostic skills this domain requires are not new. They are the same skills developed in Domain 11 (Log Reading & Diagnosis) — read the symptom, form a hypothesis, gather targeted evidence, revise — and Domain 12 (Minimum Viable Linux Administration) — navigate an unfamiliar system, identify what is running, check disk and service state. What is new is the database-specific context: the symptoms present differently, the failure modes have database-specific causes, and the wrong intervention can destroy data that cannot be reconstructed. The domain adds database literacy to existing diagnostic competence, not diagnostic competence itself.

### Boundary

Domain 5 (Storage Architecture) owns storage performance — IOPS, latency, throughput characteristics for database workloads. Domain 10 (Backup, Recovery & Resilience) owns restore-test discipline, the 3-2-1 rule, credential separation, and immutability. This domain owns the database-specific semantics that both of them gesture at but neither covers: what makes a database backup different from a file backup, why transaction logs exist and what they do to disk usage, why a VM snapshot of a running database may not be a consistent backup, and why the most common database outage is an authentication problem, not a database problem.

What is explicitly out of scope: query optimization and execution plan analysis, schema design and data modeling, database performance tuning, high-availability clustering and always-on configuration, database migration and version upgrades, and data warehousing / ETL / reporting architecture. These are DBA work or database architect work. The sysadmin who encounters these needs to recognize them and escalate, not attempt them.

## Reasoning Framework: The Database Is State, Everything Else Is Replaceable

How it is normally taught: databases are presented as applications that run on servers. You back up the server, you patch the server, you monitor the server. The database is one service among many, and the operational practices that apply to other services apply to databases.

What it is actually for: a database is the persistent state of the organization's operations. The web server can be rebuilt from a template. The application server can be reinstalled from a package. The load balancer configuration can be reconstructed from documentation. The database contains the data that cannot be reconstructed — transactions, customer records, financial history, application state. This asymmetry — the database is state, everything else is replaceable — is the reason database backup and restore semantics differ from VM-level backup and restore semantics. It is the reason transaction logs exist: to capture the sequence of state changes so that recovery can reach a consistent point rather than whatever happened to be on disk when the snapshot was taken. It is the reason "restore the VM" is not the same operation as "restore the database."

What misuse looks like: treating the database as just another application on the server. Taking a VM snapshot of a running database and calling it a backup. Assuming that because the VM was restored successfully, the database is in a usable state. Not understanding that a database's transaction log will grow without bound if backups are not configured correctly — because the database is preserving state changes, and it will not discard them until it has been told they are safely captured in a backup. The sysadmin who applies VM-level thinking to a database will eventually encounter a failure mode that VM-level thinking cannot explain.

The asymmetry manifests in operational decisions that look like special treatment but are not arbitrary. The database gets its own change window because a schema migration is not a configuration change — it is a state transformation that cannot be rolled back the way a service restart can. The database gets its own monitoring because a database that is "running" can still be failing — accepting connections but returning stale data, holding locks that block writes, running queries that consume all available memory. The database gets its own backup strategy because the question "when did we last back this up?" has a different answer at the file level (last night's backup job) and at the data level (the last transaction captured in a log backup, which may be minutes ago). These are not eccentricities of database software. They are consequences of the asymmetry, and they are the reason this domain exists separately from general application administration.

The practical implication for backup architecture: the database gets a different backup strategy than the file server, and the sysadmin who applies the same strategy to both is making a category error. The file server can be backed up with a nightly full and a VM snapshot — the files are replaceable from other sources, and the crash-consistency risk is minimal because files are not mid-transaction. The database cannot. The database needs database-native backups, log backups for point-in-time recovery, and a restore test that verifies data consistency, not just file presence. The backup strategy follows from the asymmetry: if the data is irreplaceable, the backup strategy must be designed for the data, not for the infrastructure that happens to host it.

The containerized database makes the asymmetry visible in a way that VM-hosted databases obscure. In a container orchestration environment — the context Domain 17 (Minimum Viable DevOps: Git, Containers, Orchestration) addresses — the database container is ephemeral and replaceable. The database's persistent state lives in a mounted volume, not in the container's filesystem. Destroy and recreate the container and the database comes back — as long as the volume survived. Lose the volume and the database is gone, regardless of how many container replicas the orchestrator can spin up. The "ephemeral filesystem" reflex that Domain 17 teaches for containers is the operational instance of this domain's reasoning framework: the database is state, the container is replaceable, and the backup strategy must protect the state, not the container.

*The asymmetry is the entire domain. Every concept in this chapter — transaction logs, backup types, crash consistency, connection strings — exists because the database is the one component where state cannot be reconstructed from infrastructure. Get the asymmetry right and the specific practices follow from it. Get it wrong and you will back up the wrong thing, restore the wrong thing, and be surprised when the database is in a state that the infrastructure-level backup cannot recover from.*

## Transaction Log Growth: The Classic Disk-Filler

The single most common database-related incident a sysadmin encounters is a database server that has run out of disk. The cause is almost always the same: the transaction log has grown to fill the available storage, and nobody noticed until the database stopped accepting writes.

A transaction log — called the write-ahead log in PostgreSQL, the transaction log in SQL Server, the redo log for crash recovery plus the binary log for replication and point-in-time recovery in MySQL — records every change made to the database before the change is written to the data files. This is the mechanism that provides durability, the D in ACID. The other three properties — atomicity (a transaction is all-or-nothing), consistency (a transaction takes the database from one valid state to another), isolation (concurrent transactions do not interfere) — are enforced by the database engine through locking, multiversion concurrency, and the transaction log itself. The sysadmin does not need to implement these properties. The sysadmin needs to understand that they exist, because they explain database behavior that otherwise looks irrational: why a database holds locks that block other queries, why a database refuses to accept writes when it is "running," why a database's transaction log grows even when the data files are not.

The log grows because the database will not discard committed transactions from the log until it has confirmation that they are captured in a backup. In SQL Server, this happens when the recovery model is set to Full and log backups are not being taken — the log grows without bound because the database is preserving every transaction for a backup that never comes. In PostgreSQL, the WAL accumulates if archiving is configured but the archive destination is unreachable. The database is doing exactly what it should: protecting state. The sysadmin who does not understand this will try to solve the problem by deleting log files, which is the database equivalent of deleting the undo history while the system is running.

The monitoring that catches this before it becomes an outage is not disk utilization alone — by the time disk is at 95%, the log has been growing for hours or days and the fix requires more than clearing space. The useful leading indicator is transaction log growth rate: if the log file is growing steadily between log backups, either the log backups are not running or the workload has changed and the backup frequency no longer matches the transaction volume. A database server whose disk utilization is monitored but whose log backup success is not is a server that will fill its disk predictably and without warning. This is an instance of the monitoring principle from Domain 16 (Observability & Alert Design): the alert that matters is not "disk is full" but "log backups have not succeeded in 30 minutes" — the former tells you the outage has already happened, the latter tells you it is about to.

*This is the same disk-full scenario from Domain 12 (Minimum Viable Linux Administration) — the disk is full, the service is down — but the cause and the fix are database-specific. Extending the volume with LVM buys time. Understanding why the log is growing and fixing the backup configuration is the actual remediation. A sysadmin who can do the first but not the second has solved the immediate problem and guaranteed it will recur.*

## Backup Semantics: Why a VM Snapshot Is Not a Database Backup

Database backups come in three types, and the distinction matters because each captures different state:

- **Full backup**: a complete copy of the database at a point in time. The baseline for all recovery. Large, slow, expensive — taken on a schedule measured in days or weeks, not hours.

- **Differential backup**: all changes since the last full backup. Smaller than a full backup, grows over time as more changes accumulate. Restoring requires the full backup plus the most recent differential.

- **Log backup**: the transaction log entries since the last log backup. Small, fast, taken frequently — every 5 to 15 minutes in a typical configuration. This is what provides point-in-time recovery: restore the full backup, apply the differentials, then apply log backups up to the desired moment.

The full/differential/log taxonomy maps most directly to SQL Server's recovery model. PostgreSQL uses a related but distinct model: periodic base backups (equivalent to full) plus continuous WAL archiving (equivalent to log backups), with no native differential backup type. The concepts — full, incremental-since-full, and log-level — are portable; the specific terminology and mechanism vary by engine.

Point-in-time recovery is the capability that distinguishes a database backup strategy from a file backup strategy. A file backup gives you the state of the files at the time the backup ran. A database backup strategy with log backups gives you the state of the database at any arbitrary point in time — to the second, not to the backup window. This matters when the question is "we need to recover to 2:47 PM, just before someone ran that update query."

The tradeoff between backup frequency and recovery time is the design tension in every database backup strategy. More frequent log backups mean a tighter RPO — less data lost between backups — but they also mean more log files to apply during recovery, which extends RTO. A strategy with log backups every 5 minutes and a weekly full backup may need to replay thousands of log files to reach a recovery point near the end of the week. A strategy with a daily full backup and 15-minute log backups replays far fewer logs but takes more frequent full backups, which are larger and slower. The correct balance depends on the workload's change rate, the RPO requirement, and the RTO requirement — and these are business decisions, not technical preferences.

The storage architecture for database backups connects to Domain 5 (Storage Architecture): backup storage has different performance characteristics than production database storage. Production database storage is random-read-write and latency-sensitive. Backup storage is sequential-write and throughput-oriented. Using the same storage tier for both is a mistake that D5 identifies — and for databases it is a particularly expensive mistake, because backup I/O can compete with production database I/O on shared storage and degrade the database's performance during the backup window.

The 3-2-1 rule from Domain 10 applies to database backups with a specific addition: the "two different media types" requirement should include at least one copy that is a database-native backup (not a VM snapshot or file copy), because only a database-native backup guarantees consistency. A backup architecture that relies solely on VM-level snapshots or storage-array snapshots for database protection has a crash-consistency gap that may not surface until a restore is attempted — at which point the gap becomes a data-loss event.

### The Crash-Consistency Problem

A VM snapshot captures the state of the virtual machine's memory and disk at an instant. If the database is mid-transaction — some changes written to the data files, some in memory, the transaction log partially written — the snapshot captures an inconsistent state. The database may be able to recover on startup by replaying the transaction log, or it may not. The outcome depends on what the database was doing at the exact moment the snapshot was taken, and you cannot control or predict that.

A database-aware backup uses the database's own consistency mechanism — a checkpoint, a VSS snapshot on Windows, or the database's native backup command — to ensure the backup captures a consistent state. A VM snapshot that happens to catch the database in a consistent state is lucky, not correct. A VM snapshot that catches the database mid-write may produce a backup that appears to restore successfully but contains subtle corruption that surfaces later as data integrity errors.

*This is not a theoretical concern. It is the most common reason a "backup" that was taken and verified to exist turns out to be unrestorable when it is actually needed. The backup file is present, the restore operation completes, and the database reports corruption. The VM snapshot was never a database backup — it was a crash dump of a system that happened to be running a database.*

The database-specific restore test goes beyond what Domain 10 (Backup, Recovery & Resilience) describes for VM-level recovery. A VM restore test that confirms "the database service is running" has not validated that the database is usable. The database-specific success criteria include: the database starts without errors (no torn-page recovery, no transaction log corruption), the data is consistent to a known point in time (run a row count or checksum against a known-good value), the application can connect and execute queries (not just that the port is open), and — critically for point-in-time recovery — a restore to an arbitrary intermediate timestamp produces the expected data state. A restore test that does not include point-in-time verification has not tested the capability that distinguishes a database backup from a file backup.

Consistency verification after a restore is the step that most organizations skip. "The database started" is not "the data is correct." A database that starts successfully after a restore may have silent corruption — pages that were mid-write when the backup was taken, transactions that were partially committed, indexes that are out of sync with the data files. Most databases provide a consistency-check command (DBCC CHECKDB in SQL Server, pg_amcheck or a manual checksum comparison in PostgreSQL, CHECK TABLE in MySQL). Running this command after a restore and before declaring the recovery complete is the difference between a tested restore and a hoped-for restore. Domain 10's principle — an untested backup is functionally equivalent to no backup — has its database-specific instance here: a restore that was not consistency-checked is a restore of unknown quality.

## Connection Strings and Auth Failure Modes

The most common database-related outage — meaning the service is down and users are affected — is not a database problem. It is an authentication problem that manifests as a database problem. The application cannot connect to the database, the monitoring alerts on database unavailability, and the sysadmin is paged — but the database is running fine and the problem is in the connection configuration.

A connection string specifies: the database server's address, the port, the database name, the authentication credentials, and a set of options that affect behavior. Each of these can fail:

- **Wrong server or port**: the database moved, the DNS record changed, the port was reconfigured. The application gets connection refused or timeout. The database is fine.

- **Expired credentials**: the service account password was rotated and the application's connection string was not updated. Or the credential expired automatically per policy. The database is fine; the application cannot authenticate.

- **TLS/certificate failure**: the database certificate was renewed and the application does not trust the new CA, or the certificate expired and was not renewed. The connection fails at the TLS handshake. The database may be fine; the certificate is not.

- **Permission revoked**: someone removed the service account's access to a table or schema, or the database was restored from a backup that predates the account's creation. The application connects but queries fail with permission denied.

- **Connection pool exhaustion**: the application's connection pool is exhausted — too many connections, connections not being released, a query holding locks that block other connections. The database is up but cannot accept new connections. This is the one that looks like a database problem and actually is, but the fix may be in the application's connection management, not the database.

Connection strings also present a security concern that is often overlooked. A connection string in a configuration file contains credentials — typically a service account with direct database access. That file is often version-controlled, readable by the development team, and sometimes deployed to servers where the application runs with broader access than intended. The connection string is a credential store, and the credentials it contains are a path to the organization's data. Domain 8 (Security Reasoning) applies: the risk of credential exposure in config files should be evaluated and mitigated — through secret management, managed identities, or at minimum file-level access controls that limit who can read the connection string. A connection string committed to a git repository is a credential leak, even if the repository is private.

Connection pooling — the `Max Pool Size` parameter in a connection string — is an application-side concern that becomes a database-side problem when it is misconfigured. A connection pool that is too small produces connection timeouts under load. A pool that is too large consumes database memory and can exhaust the database's connection limit, causing all applications sharing the database to fail. The sysadmin does not tune the pool, but should recognize that intermittent connection failures under load may be a pool-size problem, not a database-availability problem — and that the fix is in the application configuration, not the database.

*The diagnostic discipline: before touching the database, verify the connection string. Check whether the database is accepting connections from the application's host using the application's credentials. Check whether the credentials are valid. Check whether the certificate is current. Most "database is down" pages are resolved without touching the database at all.*

The diagnostic sequence matters because the order in which you check determines how fast you resolve the outage. Start with the error message — "Login failed" is an auth problem, "Connection refused" is a network or service problem, "Timeout" is a network or firewall problem, "Permission denied" after successful connection is a permissions problem. Each error message points to a different layer, and checking the wrong layer first wastes the first ten minutes of the outage. The sysadmin who reads the error message and forms a hypothesis before acting is applying the same diagnostic discipline that Domain 11 (Log Reading & Diagnosis) teaches — the symptom is the starting point, not the conclusion.

## The Read Replica Is Not a Backup

Domain 10 (Backup, Recovery & Resilience) establishes that a replica is not a backup. The database-specific instance of this rule deserves explicit treatment because it is the one place sysadmins most commonly mistake replication for protection.

A read replica maintains a continuously updated copy of the database. It is useful for read scaling and for availability — if the primary fails, the replica can be promoted. But it is not a backup because it replicates state changes in real time. If a table is accidentally dropped on the primary, it is dropped on the replica within seconds. If data is corrupted by a bad query, the corruption propagates to the replica. If ransomware encrypts the database, the replica is encrypted too.

A read replica provides availability, not recovery. It protects against the primary's hardware failing. It does not protect against the data on the primary being wrong. These are different failure modes requiring different controls, and the control for data-level recovery is a backup with point-in-time capability stored on separate infrastructure with separate credentials — exactly what Domain 10 specifies.

This does not make read replicas useless. A read replica is the correct tool for read scaling — offloading reporting queries from the primary so they do not compete with transactional workload. It is the correct tool for availability — promoting the replica when the primary fails, reducing downtime from hours to minutes. It is the correct tool for planned maintenance — failing over to the replica while the primary is patched. What it is not is a recovery mechanism for data loss. The sysadmin who understands this distinction can advocate for replication where it helps and insist on backups where replication does not — and these are different conversations with different stakeholders.

## Database Behavior the Sysadmin Will Encounter

The following behaviors are the ones most likely to trigger a "is this a database problem?" question, and understanding them is prerequisite to knowing when to call a DBA.

A database that is "running" can still be failing in ways that do not produce a service-down alert. The sysadmin who inherits database monitoring needs to recognize the behaviors that indicate problems without needing to diagnose their root cause. These behaviors are not things the sysadmin fixes — they are things the sysadmin routes correctly, to the DBA or to the development team, with enough context that the right person can act immediately.

- **Locking and blocking.** When one transaction holds a lock on a row or table, other transactions that need the same resource wait. Short waits are normal. Long waits produce blocking chains — the first transaction blocks the second, the second blocks the third, and the application appears slow or unresponsive to users. The sysadmin's job is not to tune locking behavior — that is DBA work. The sysadmin's job is to recognize that "the application is slow" may be a database locking problem, not a network problem or a server resource problem.

- **Deadlocks.** Two transactions each holding a lock the other needs. The database detects this and kills one of them — the application sees an error. Intermittent deadlocks are often a sign of an application-level query ordering problem, not a database configuration problem. The sysadmin should report the deadlock pattern to the DBA or development team, not attempt to resolve it by changing database configuration.

- **Long-running transactions.** A transaction that stays open for minutes or hours holds locks, prevents log truncation, and can cause the same disk-full scenario as a missing log backup schedule. The cause is usually application-side — a query that opened a transaction and did not commit it, or a report that holds a read lock for the duration of a large scan. The sysadmin who sees transaction log growth with log backups apparently running correctly should check for long-running transactions as a secondary cause.

- **Stale statistics.** Database query optimizers use statistics about data distribution to choose execution plans. When statistics are stale — after a large data load, a bulk delete, or simply because the statistics update job has not run — the optimizer may choose a catastrophically bad plan, and a query that ran in seconds yesterday takes minutes today. This looks like a sudden database performance problem. It is, but the fix is a statistics update, which is DBA work. The sysadmin should recognize that sudden performance degradation without a configuration change may be stale statistics and route accordingly.

These behaviors are not problems the sysadmin fixes. They are problems the sysadmin recognizes and routes correctly — to the DBA for database-level diagnosis, to the development team for application-level causes, or to monitoring for alerting on the symptoms before users notice. The routing decision is itself a competency: the sysadmin who pages the DBA for a locking problem that is caused by an application query is wasting the DBA's time. The sysadmin who pages the development team for a stale-statistics problem is wasting the development team's time. Getting the routing right requires understanding enough of the failure mode to identify which layer owns it — and that is exactly what this domain's level ladder assesses.

## When to Call a DBA

The boundary between minimum viable database administration and specialist work is not a line — it is a judgment call that depends on the context, the stakes, and the available expertise. The following are beyond the MV floor:

- **Query performance tuning.** A slow query consuming resources requires understanding execution plans, index strategy, and statistics — this is DBA work, not sysadmin work. The sysadmin's job is to identify that the problem is a query performance problem, not a storage or network problem, and escalate.

- **Schema changes.** Adding a column, modifying a data type, or restructuring tables on a production database requires understanding locking behavior, migration strategies, and rollback planning. This is not a configuration change; it is a data architecture decision.

- **Replication topology design.** Setting up a read replica is within the MV floor. Designing a multi-region replication topology with conflict resolution and failover automation is specialist work.

- **Database patching and version upgrades.** Applying an operating system patch to a database server is sysadmin work. Applying a database engine patch or version upgrade is not — it requires understanding of upgrade paths, breaking changes, schema compatibility, and rollback procedures that are specific to the database engine and version. The sysadmin's role is to coordinate the maintenance window, verify the backup before the patch, and confirm the database is functional after. The DBA's role is to perform the upgrade and verify application compatibility.

- **Corruption recovery.** If the database reports corruption — torn pages, checksum failures, inconsistent system catalogs — stop. Do not attempt repair with generic tools. Call a DBA. The difference between a correct repair and an incorrect one is the difference between recovering all data and losing it permanently.

The cost of not escalating is not symmetrical with the cost of escalating unnecessarily. A DBA woken at 3 AM for a problem the sysadmin could have handled is annoyed but the database is fine. A sysadmin who attempts a corruption repair, a schema migration, or a replication reconfiguration without specialist knowledge can cause data loss that is irreversible. The asymmetry mirrors the domain's reasoning framework: the database is state, and state once lost cannot be reconstructed. When in doubt, escalate. The DBA would rather be called for a problem that turns out to be simple than discover that a simple problem was made catastrophic by an intervention that should not have been attempted.

There is a gray zone between the MV floor and specialist work: index rebuilds, statistics updates, database configuration tuning, and connection limit adjustments are tasks that an experienced sysadmin may handle on a database they know well, and that a junior sysadmin should not attempt on any production database. The boundary is not the task itself but the practitioner's understanding of what the task does, what can go wrong, and how to verify it worked. A sysadmin who rebuilds an index and can explain why it was needed, what the rebuild does to concurrency, and how to verify the result has crossed into DBA territory competently. A sysadmin who runs a command they found online without understanding any of those three things has not.

*The sysadmin who can identify that a problem is beyond the MV floor and escalate correctly has demonstrated more competence than the one who attempts a fix they do not fully understand. Calling a DBA is not a failure of the domain — it is the domain's highest-level skill correctly applied.*

When escalating, provide the DBA with what they need to act immediately rather than discovering the problem from scratch: the exact error message, when it started, what changed recently (patching, configuration changes, application deployments), what has been tried and what the result was, and what the business impact is. This is the commissioning discipline from Domain 1 (Scripting & Automation) applied to escalation: a clear statement of the problem, the context, and the constraint, delivered to the person who can solve it. The sysadmin who pages a DBA with "the database is broken" has wasted the first ten minutes of the DBA's response time. The sysadmin who pages with "the orders database is refusing connections since 10:15 AM, the error is 'Login failed for user svc_orders,' no changes were deployed this morning, the application is down for all 200 users" has given the DBA a head start that may be the difference between a 15-minute fix and a 2-hour investigation.

## Assessment Exercises

### [LITERACY] The Connection String and the Backup Config

*Candidate is given a connection string from an application configuration file and a backup job configuration. The connection string is: `Server=db-prod-01.internal;Database=orders;User Id=svc_orders;Password=*****;Encrypt=true;TrustServerCertificate=false;Max Pool Size=100`. The backup job runs nightly at 2:00 AM, takes a full backup of all databases on the server, retains 14 days, and stores backups on a network share. Candidate must: identify what database software is running, what the connection string reveals about the authentication and encryption configuration, what the backup job actually backs up, and what recovery capabilities this configuration provides and does not provide.*

**Watch for:** Candidates who cannot identify SQL Server from the connection string syntax — the semicolon-delimited key=value pairs with Server/Database/User Id are SQL Server conventions; PostgreSQL and MySQL use different formats. Candidates who do not recognize that `TrustServerCertificate=false` means the application validates the database server's certificate against a trusted CA, and that if the certificate expires or the CA is not trusted, connections will fail — this is a common outage cause. Candidates who describe the nightly full backup as sufficient without noting that it provides no point-in-time recovery: the organization can only recover to the last 2:00 AM backup, losing all transactions since then. Candidates who do not flag that 14-day retention may be insufficient depending on the ransomware dwell-time threat model from Domain 10 (Backup, Recovery & Resilience). A candidate who can read the connection string, identify the database type, describe what the backup configuration does and does not provide, and identify the gap between what the configuration provides and what point-in-time recovery would require is demonstrating Level 1 competence. A candidate who also recognizes that the connection string contains a plaintext password and flags the credential exposure risk is exceeding Level 1 and touching Level 2 (Security Reasoning cross-domain awareness).

### [AUDIT] The Database That Filled the Disk

*A monitoring alert reports that the database server db-prod-01 is at 98% disk utilization on its data volume. The database is refusing writes. The server runs SQL Server with the recovery model set to Full. The backup job runs nightly full backups. No log backups are configured. The server also has a VM-level snapshot backup taken by the hypervisor every night. A read replica exists on db-replica-01. Candidate must: identify the cause of the disk exhaustion, explain why the VM snapshot is not a reliable database backup, explain why the read replica is not a backup, and describe the correct remediation.*

**Watch for:** Candidates who recommend extending the disk or deleting log files without understanding why the log is growing. The cause is the Full recovery model without log backups — SQL Server preserves every transaction in the log until a log backup truncates the committed entries. The fix is to configure log backups on a frequent schedule (every 5–15 minutes), which both truncates the log and provides point-in-time recovery. Candidates who accept the VM snapshot as a backup without addressing the crash-consistency problem — the snapshot may capture the database mid-transaction, producing a backup that is inconsistent or corrupt. Candidates who point to the read replica as a backup without recognizing that it replicates all changes including destructive ones — a dropped table on the primary is dropped on the replica within seconds.

Candidates who recommend only extending the disk without fixing the backup configuration have treated the symptom, not the cause. Extending the disk is a valid emergency measure — it buys time — but without configuring log backups the log will fill the new space too. The correct remediation has two phases: emergency (extend the disk or shrink the log if possible to restore service) and root cause (configure log backups on a regular schedule so the log truncates going forward). A candidate who articulates both phases and explains why the emergency measure alone is insufficient is demonstrating Level 2 reasoning. A candidate who identifies all three issues — log growth cause, VM snapshot inconsistency, replica-is-not-backup — and explains the correct remediation is demonstrating strong Level 2.

### [COMMISSION] Specify the Backup Strategy

*Candidate must specify a database backup strategy for a business-critical order processing database with the following requirements: the business can tolerate losing no more than 15 minutes of transactions (RPO), the database must be recoverable within 4 hours (RTO), and the organization needs to be able to recover to any point in time within the last 30 days. The database is PostgreSQL. Candidate must specify: the backup types and schedule, the retention policy, where backups are stored and with what credential separation, and what the restore test plan looks like including database-specific success criteria.*

**Watch for:** Specifications that prescribe only full backups without WAL archiving — this cannot meet a 15-minute RPO. The correct strategy includes: a regular base backup (daily or weekly), continuous WAL archiving with a checkpoint interval that supports 15-minute recovery granularity, 30-day retention for both base backups and WAL archives, storage on separate infrastructure from the database with separate credentials per Domain 10's requirements, and a restore test plan that validates not just that the database starts but that the data is consistent and complete — including restoring to a specific point in time and verifying the data matches the expected state at that moment. Candidates who specify a restore test that only checks "database is running" without verifying data consistency or point-in-time recovery capability have not understood the database-specific semantics. Candidates who articulate the tradeoff between backup frequency and storage cost — more frequent base backups reduce recovery time (less WAL to replay) but increase storage cost — are demonstrating the tradeoff articulation the rubric rewards. Candidates who address the credential separation requirement by name, specifying that the backup account cannot delete backups and that the backup storage is on a separate trust tier from the database server, have connected the database-specific backup strategy to Domain 10's immutability and credential separation requirements. A candidate who produces a complete specification with correct backup types, schedule, retention, credential separation, and a meaningful restore test plan is demonstrating Level 3 competence.

### [ADAPTATION] The Outage Triage

*At 10:30 AM on a Tuesday, the order processing application stops working. The monitoring alert says "database connection failed." The database server is running — CPU is normal, memory is normal, disk has 40% free. The application logs show "Login failed for user 'svc_orders'" repeated every few seconds. The database's transaction log has been growing steadily since 9:45 AM. The DBA is in a meeting and will not be available for 30 minutes. Candidate must describe their triage sequence: what they check, what they try, what they do not touch, and at what point they interrupt the DBA's meeting.*

**Watch for:** Candidates who immediately try to restart the database. The database is running fine — the problem is authentication, not the database service. The "Login failed" error points to a credential problem: the service account password may have expired or been rotated, or the account may have been locked. The first check is whether the credentials in the application's connection string are valid — can you connect to the database using those credentials from the application server? The transaction log growth is a separate issue — log backups may have stopped, or a long-running transaction may be preventing log truncation. The candidate should not assume the auth failure and the log growth share a common cause without evidence. The candidate should not attempt to fix the log growth by truncating the log or deleting files.

The escalation decision is where tradeoff articulation matters: the candidate should interrupt the DBA when the credential issue is confirmed and the fix requires DBA involvement (resetting the password, unlocking the account, verifying permissions), or when the log growth threatens to fill the disk before the DBA is available — estimate the growth rate against remaining capacity and make a defensible call. A candidate who argues for waiting because "the DBA will be here in 30 minutes and the disk has 40% free" should be able to articulate the growth-rate calculation that makes that defensible: if the log is growing at 2% per hour, 40% free gives 20 hours of runway — waiting is defensible. If the log is growing at 10% per hour, 40% free gives 4 hours — still defensible but tighter. If the candidate cannot estimate the growth rate, they cannot make the call, and the defensible action is to escalate now rather than guess.

A candidate who correctly identifies this as an auth problem, takes the right diagnostic steps without touching the database, and makes a defensible escalation decision with articulated reasoning is demonstrating Level 4 reasoning — the ability to triage under pressure and reason about when the problem exceeds the MV floor. The candidate who reaches the right conclusion ("call the DBA") without articulating the tradeoff has not demonstrated the same skill as the candidate who reasons through the growth-rate calculation and the escalation threshold.
