## On the project

The platform is well-architected for its stage — the Schema V2.0 scenario format is clean, the orchestrator abstraction is sound, and the calibration harness is thoughtful. The breadcrumb system (47 tracked issues) provides excellent visibility into known technical debt. The gap between "code exists" and "code is wired correctly" is the recurring pattern: the Proxmox orchestrator had a complete interface and dry-run support but was never connected to production config (vm_name_to_id), and SEC-03 was already partially fixed (non-local routing) but the guard was missing. The project benefits from the adversarial review practice — it caught real bugs that the implementation agents missed.

## On the work done

**Confident in:**
- Proxmox orchestrator implementation — 101 tests cover dry-run, HTTP calls, task polling, guest agent ops, error handling, and all the adversarial fixes (SSL default, timeouts, null handling, URL encoding, temp cleanup)
- SEC-03 fix — simple, correct guard with clear error message
- Calibration harness — mixed-signal and variance features are backward-compatible and well-tested
- Validate-only mode — structural validation catches real issues (found pre-existing missing severity fields)

**Less confident in:**
- Scenario content quality — the adversarial review found factual issues (CT monitoring for corp.local, inconsistent cert counts, response_level_2 contradicting its indicator). We fixed all of these, but scenario authoring is inherently subjective and a domain expert might find more issues
- Proxmox form encoding — the adversarial review flagged that `command: ["/bin/bash", path]` as form data might not be correctly interpreted by the Proxmox API. Tests mock at the Python level, so encoding bugs are invisible. This needs validation against a real Proxmox API
- The `run_script_in_guest` cleanup — we added UUID-based filenames and rm cleanup, but if the guest agent exec for cleanup fails, the temp file leaks silently

## On what remains

1. **Real Proxmox API validation** — the orchestrator has never been tested against a real Proxmox cluster. Form encoding (list/boolean parameters) may differ from what the Perl-based Proxmox API expects. This is the highest-risk gap.
2. **Calibration with real API keys** — WI-005 documented the limitation and added --validate-only, but the scenarios still need actual calibration runs against Sonnet/Opus to verify rubric quality. The new mixed-signal responses especially need calibration.
3. **Scenario coverage** — D13 still has only 2 scenarios. Plan 001 Phase 1 calls for Domains 15-18 authoring, which is a substantial content effort.
4. **Pre-existing test failures** — 4 test modules fail due to missing Python dependencies (anthropic, sqlalchemy, pydantic_settings). These are environment issues, not code bugs, but they mean CI can't run the full suite.
5. **d15/d06 untracked files** — scenarios from prior sessions (d06 expanded, d15 synced) are in the working tree but were never committed. They should be included in this commit.

## Gaps to flag

- **`orchestrator_proxmox.py:355-359`** — `data={"command": ["/bin/bash", remote_path]}` may not form-encode correctly for Proxmox's Perl API. Needs real API testing.
- **`orchestrator_proxmox.py:349`** — `data={"encode": True}` sends Python `True` as form string `"True"`. Proxmox may expect `1` or `true`.
- **`calibration/run.mjs:148-159`** — `getArg()` doesn't validate that the next token after a flag isn't itself a flag. `--provider --level 2` silently sets provider to `"--level"`.
- **`evaluator.js:14`** — `INTERNAL_LOCAL_ENDPOINT = 'http://192.168.1.28:1234/v1'` is a hardcoded developer-specific IP. Other developers will have a non-functional default.
- **`evaluator.js:75`** — `buildClient({ provider = 'local', ... })` defaults to `'local'`, so omitting the provider silently creates a browser-side client. The guard checks the name, not the endpoint — a user could set `provider: 'local'` with a real commercial endpoint and API key.
- **Breadcrumbs drift** — several breadcrumb files (arch-04, arch-05, eval-03, sec-05, sec-06) were updated by the prior session's drift audit but never committed. They're staged in this commit.
