The immediate cause of the disk exhaustion is uncontrolled transaction log growth. The `orders` database is in FULL recovery model, but only nightly full backups are configured. In FULL recovery, SQL Server keeps every committed transaction in the log until a log backup truncates it. Because no log backups exist, the log has grown from 38.2 GB on 2026-07-20 to 437.2 GB today. Error 9002 explicitly says the log is full due to 'LOG_BACKUP', which points directly at the missing log-backup job.

The nightly VM-level snapshot is not a reliable database backup on its own. The hypervisor takes a checkpoint of a running VM with no VSS writer or application-consistent backup agent installed. If SQL Server is mid-transaction when the snapshot is captured, the resulting image can contain torn pages, partially written log records, and uncommitted changes. The database might start after a restore but contain corruption that only surfaces later. A usable database backup must be coordinated by the database engine.

The read replica on db-replica-01 is also not a backup. It replicates changes from the primary in near real time. If a table is dropped, data is corrupted by a bad query, or files are encrypted by ransomware, those changes will propagate to the replica within seconds. The replica is useful for read scaling and could be promoted for availability, but it does not provide point-in-time recovery or protection against logical data loss.

Before the DBA arrives the priority is to prevent the volume from hitting 100%. The safest emergency action is to extend the E: drive, because that restores write capability without risking database consistency. Once the DBA is on site, they should take a transaction log backup and then configure a recurring log-backup job on a frequent schedule so the log truncates normally going forward. Only extending the disk without adding log backups would guarantee the same outage happens again.
